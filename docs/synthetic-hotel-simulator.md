# Synthetic hotel development simulator

The simulator exercises Model 1 predictions, PSI/KS monitoring, synthetic
cancellation outcomes, and a chronological Model 2 development evaluation. It
generates artificial data only; it is not a hotel/PMS integration and does not
produce genuine production observations or labels.

Every booking, prediction, outcome, monitoring report, Model 2 row, and run
summary is tagged:

```text
data_source_type=synthetic
source=synthetic_simulator
environment=development
is_synthetic=true
```

The simulator does not call either production ingestion endpoint, use the
production ingestion token, run the production Model 2 trainer, or write under
the production monitoring/model directories. Its Model 2 dataset uses
monitoring-time features and previously observed performance only; simulated
cancellation outcomes are generated by applying a controlled noise rate to
Model 1 predictions, so apparent performance changes are deliberately scripted,
not independent evidence about a real hotel population. Labels are added after
the feature snapshot. Training and holdout batches are
chronologically separated, and both target classes are required in each
partition. These results are workflow demonstrations, not estimates of
real-world model performance.

## Run a simulation

From the project root in PowerShell:

```powershell
python -m ml.synthetic_hotel_simulator --batches 24 --batch-size 160 --seed 42
```

At least 20 batches are required. The defaults generate 24 chronological
batches of 160 bookings each. Each invocation gets a new run directory, so
existing simulation outputs and model artifacts are not overwritten. To use a
different deterministic seed or output root:

```powershell
python -m ml.synthetic_hotel_simulator --batches 24 --batch-size 160 --seed 7 --output-root "data\development_simulation\runs"
```

Outputs are stored below
`data/development_simulation/runs/<unique-run-id>/`. They include per-batch
booking CSVs, prediction/outcome JSONL files linked by `observation_id`, PSI/KS
monitoring reports, the Model 2 development dataset, chronological holdout
predictions, and a run summary. The development model artifact is stored inside
that unique run directory, not in the existing Model 2 development artifact
folder.

After running the backend, open or refresh the dashboard. The **DEVELOPMENT
SIMULATION** panel displays the latest completed, provenance-validated run.
This panel is visually separate from **PRODUCTION Model 2**. Synthetic batches
remain ineligible for the unchanged requirement of at least 20 distinct
genuine labeled production batches.

## Verify the isolated workflow

From the project root:

```powershell
pytest ml\tests\test_synthetic_hotel_simulator.py ml\tests\test_model2_development_training.py backend\tests\test_dashboard_api.py backend\tests\test_model1_api.py -q
```

The tests cover deterministic generation, batch chronology and linkage,
synthetic provenance, prediction/outcome records, drift and performance
simulation, both Model 2 target classes in chronological train/holdout
partitions, dashboard labeling, and exclusion from production ingestion and
training eligibility.
